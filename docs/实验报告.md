# UNIX V6++ 页表系统与位示图内存分配实验报告

## 一、实验要求

本次实验以修改版 UNIX V6++ 操作系统为基础，在已有内核、文件系统、进程管理和用户程序运行机制之上，对内存管理部分进行改造和完善。实验的核心要求包括两个方面：一是修改并完善页表系统，二是将原有内存分配方式改为位示图管理方式。

具体要求如下：

1. 阅读课程设计要求和现有 UNIX V6++ 源码，理解系统启动、分页初始化、进程创建、用户程序装载、文件系统镜像生成等基本流程。
2. 修改页目录和页表相关数据结构，使其符合 x86 32 位分页机制下页目录项、页表项 4 字节对齐和 1024 项一页的基本要求。
3. 在系统启动阶段正确建立页目录、内核页表和必要的地址映射，使内核能够在开启分页后继续运行。
4. 为用户进程建立独立的页目录和用户页表，使不同进程可以拥有相对独立的用户地址空间。
5. 修改 fork、exec、进程退出、内存释放等流程，使其能够配合新的页表系统正常工作。
6. 将物理页分配方式从传统空闲表方式改为位示图方式，用 bit 标记每个物理页是否被占用。
7. 重新构建磁盘镜像，并在 QEMU 中启动系统，验证 Shell、malloc、fork、ls、date 等用户程序能够正常运行。

本实验最终目标是：修改后的系统能够成功编译、生成镜像、在 QEMU 中启动进入 Shell，并通过用户程序验证页表系统和位示图分配机制已经能够正常工作。

## 四、代码部分关键改进

### 4.1 位示图内存分配方式

原 UNIX V6++ 中部分内存管理逻辑沿用了空闲表思想，通过记录空闲区起始地址和长度来完成分配。这种方式适合连续空间管理，但在分页系统中，物理内存通常以固定大小页框为单位进行管理，因此使用位示图更直观。

本次实验中，主要在以下文件中实现位示图分配：

```text
include/MapNode.h
include/Allocator.h
mm/Allocator.cpp
include/PageManager.h
mm/PageManager.cpp
```

在 `include/MapNode.h` 中增加了 `BitMap` 数据结构。该结构使用一个整数数组保存页框占用状态，每个 bit 对应一个物理页：

```text
bit = 0：该页空闲
bit = 1：该页已被占用
```

`BitMap` 中保存了两个关键字段：

```text
m_AddressIdx：位示图所管理物理页池的起始地址
m_PageCount：位示图所管理的页数量
```

在 `mm/Allocator.cpp` 中实现 `BitMapAllocator`，其核心操作包括：

```cpp
int BitMapAllocator::is_free(BitMap &bitmap, int index);
void BitMapAllocator::set_bit(BitMap &bitmap, int index, int value);
unsigned long BitMapAllocator::Alloc(BitMap &bitmap, unsigned long size);
unsigned long BitMapAllocator::Free(BitMap &bitmap, unsigned long size, unsigned long addrIdx);
```

`Alloc()` 的基本思路是：

1. 根据申请字节数计算需要的页数。
2. 从位示图起始位置开始扫描连续空闲 bit。
3. 找到足够长的连续空闲页后，将这些 bit 置为 1。
4. 返回对应的物理页起始地址。

`Free()` 的基本思路是：

1. 根据释放地址计算其在位示图中的页号。
2. 根据释放大小计算需要释放的页数。
3. 将对应 bit 清零。

在 `mm/PageManager.cpp` 中，内核页管理器和用户页管理器改为使用 `BitMapAllocator`。例如：

```text
KernelPageManager：管理内核页池
UserPageManager：管理用户页池
```

这样修改后，物理页是否被占用可以通过位示图快速判断，页级分配逻辑也更符合分页内存管理机制。

### 4.2 页目录和页表结构调整

页表系统相关代码主要位于：

```text
include/PageTable.h
include/PageDirectory.h
machine/Machine.cpp
include/Machine.h
```

在 x86 32 位分页机制中，一个页目录项和一个页表项都应为 4 字节，每个页目录或页表包含 1024 项。实验中对 `PageTableEntry` 和 `PageDirectoryEntry` 进行了调整，保证位域基础类型使用 32 位无符号整数，从而使页表项和页目录项大小符合硬件要求。

系统启动阶段的页目录初始化在 `Machine::InitPageDirectory()` 中完成。该函数负责：

1. 初始化页目录所在物理页。
2. 初始化内核页表。
3. 建立低地址映射，保证刚开启分页后当前执行代码仍然可访问。
4. 建立高地址内核映射，使内核可以运行在 `0xC0000000` 以上的高地址空间。

分页开启函数为：

```cpp
void Machine::EnablePageProtection()
```

该函数主要完成：

1. 将页目录物理地址写入 CR3。
2. 设置 CR0 的 PG 位。
3. 开启分页机制。

在 `kernel/main.cpp` 中，必须保证调用顺序正确：

```cpp
machine.InitPageDirectory();
machine.EnablePageProtection();
```

如果页目录未正确初始化，或开启分页调用被注释、遗漏，系统会在加载段寄存器或跳转高地址代码时发生异常，严重时会出现 triple fault。本次实验中对该启动路径进行了修正，最终系统能够稳定进入 Shell。

### 4.3 用户进程私有页表和页目录

进程页表管理相关代码主要位于：

```text
proc/MemoryDescriptor.cpp
proc/ProcessManager.cpp
proc/Process.cpp
include/MemoryDescriptor.h
include/Process.h
include/ProcessManager.h
```

实验中为用户进程增加了私有页表和页目录管理逻辑。关键函数包括：

```cpp
PageDirectory *ProcessManager::AllocPageDirectory();
void ProcessManager::InitProcPageDirectory(Process *proc, PageTable *privateUsrPageTable);
void MemoryDescriptor::MapToPageTable();
```

`AllocPageDirectory()` 用于为进程申请新的页目录空间。页目录本身由内核页管理器分配，因此也会经过位示图分配器。

`InitProcPageDirectory()` 用于初始化某个进程的页目录。页目录中需要同时映射：

1. 用户空间页表。
2. 内核空间页表。
3. 当前进程私有用户页表。

这样，每个进程在运行时可以拥有独立的地址空间，而内核空间仍然保持共享映射。

`MemoryDescriptor::MapToPageTable()` 用于将当前进程的用户页表映射更新到硬件使用的页目录中，并通过刷新 CR3 使新的映射生效。该函数在 exec、fork、进程切换等路径中都会发挥作用。

### 4.4 fork、exec 和缺页异常处理

用户程序运行和进程创建主要涉及：

```text
proc/ProcessManager.cpp
proc/Process.cpp
interrupt/Exception.cpp
```

在 `fork` 过程中，系统需要为子进程建立进程结构、页目录和用户页表。实验中修改了 `ProcessManager::NewProc()` 相关逻辑，使父子进程能够正确处理页表关系。

在写时复制相关逻辑中，fork 后父子进程可以暂时共享相同物理页，并将页表项写权限关闭。当进程后续尝试写入共享页时，会触发缺页异常。缺页异常处理程序位于 `interrupt/Exception.cpp`，其处理思路如下：

1. 读取 CR2，获得发生缺页的线性地址。
2. 判断该地址是否属于用户进程私有页表管理范围。
3. 判断页表项是否为写时复制场景。
4. 如果物理页只被当前进程引用，则恢复写权限。
5. 如果物理页被多个进程共享，则分配新物理页，复制原页内容，并更新当前进程页表项。

该机制可以减少 fork 时的立即复制开销，同时也验证了页表权限位、缺页异常、物理页分配和进程地址空间之间的协同工作。

### 4.5 镜像生成和设备访问修正

在调试过程中，为保证系统能在当前 QEMU 环境中稳定运行，还对镜像生成和磁盘访问进行了修正。

涉及文件包括：

```text
dev/DMA.cpp
include/PEParser.h
tools/v6pp-fs-edit-2022/build_image.py
```

在 `dev/DMA.cpp` 中，启用 IDE PCI 设备的 I/O space 和 bus master 位：

```cpp
command |= 0x00000005;
```

该修正确保 QEMU 中 IDE 磁盘 DMA 访问正常。如果未启用相关位，系统在打开 `/dev/tty1` 或读取文件系统数据时可能出现异常，表现为启动阶段报 `STDIN Error`。

在 `include/PEParser.h` 中，根据当前 MinGW 生成的 PE 文件 section 顺序调整相关索引，使用户程序加载时能够正确识别 `.text`、`.data`、`.rdata`、`.eh_frame`、`.bss` 等段。

在 `build_image.py` 中，完善了小文件写入镜像的逻辑，使其在超过直接块数量后能够正确使用一级间接块。该修正保证了 `Shell.exe` 等较大文件能够完整写入镜像，否则系统可能出现 Shell 读取不完整或 exec 失败的问题。

## 七、实验心得

本次实验让我对操作系统中内存管理、分页机制和进程地址空间有了更具体的认识。相比普通应用程序开发，操作系统实验中的每一处数据结构都与硬件行为密切相关。例如页表项和页目录项必须严格符合 4 字节格式，CR3 中必须写入页目录物理地址，CR0 的分页位必须在页表准备完成后才能开启。这些细节一旦出错，系统往往不是输出普通错误信息，而是直接启动失败、异常重启或 triple fault。

位示图分配方式也让我更直观地理解了页式内存管理。原来的空闲表方式通过起始地址和长度描述空闲空间，适合连续区间管理；而分页系统中物理内存天然被划分成固定大小的页框，因此使用一个 bit 表示一个页框的状态更加自然。通过 `malloc` 测试看到 heap 扩展，能够把用户态内存申请和内核中的物理页分配联系起来，也更加理解了用户空间虚拟地址和物理内存之间并不是一一固定对应的关系。

进程页表部分是本次实验中较复杂的内容。fork、exec、进程退出和缺页异常看似属于不同模块，但它们都依赖页表系统正确工作。fork 时需要处理父子进程地址空间关系，exec 时需要重新建立用户程序的代码段、数据段和栈映射，进程退出时需要释放页表和物理页，缺页异常则需要根据错误地址和页表项状态做出正确处理。这些流程串联起来后，才能保证 Shell 和用户程序稳定运行。

调试过程也体现了操作系统开发的特点。最初出现的 `STDIN Error` 表面上是标准输入打开失败，但进一步分析后发现与磁盘 DMA、文件系统镜像和用户程序装载都有关系。后来系统停在 `Booting from Hard Disk...` 或出现 triple fault，也需要结合 QEMU 日志、反汇编和启动流程逐步定位。通过这些调试，我认识到操作系统问题往往不能只看表面现象，而要沿着启动路径、硬件状态和内核数据结构逐层分析。

最终，系统能够成功启动并运行 `malloc`、`fork`、`ls`、`date` 等程序，说明页表系统和位示图分配机制已经能够配合其他内核模块正常工作。本次实验不仅完成了代码功能，也加深了我对分页、物理页管理、进程地址空间、文件系统镜像和 QEMU 调试方法的理解。
